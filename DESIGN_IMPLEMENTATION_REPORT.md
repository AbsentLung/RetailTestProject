# Design Implementation Report

`DESIGN_PROPOSAL_FINAL.md` describes the bonus round's design; `DESIGN_REVIEWED_PROPOSAL.md` is the record of what was questioned and corrected before and during the build. This document is what actually happened: what held up exactly as planned, the real bugs that only showed up by running the thing rather than reading the code, a place the build didn't match the proposal (fixed), a place the build matched the proposal and the proposal was the problem (also fixed, by changing course), and six rounds of external review that each caught something real.

## What got built, in order

Option A ("Quiet Ledger" - responsive layout, dark theme via `prefers-color-scheme`); alerts filters (status and brand); keyset pagination for alerts and tracking-event lists; CSV export of alerts; sortable columns everywhere, including alerts (a generalized keyset mechanism supporting any column, either direction, including joined and computed ones) and, on the store show page, Brand too, linked to its own page; filtering and sorting on the tracking-event lists (inventory present, a date range, a store/product dimension); a scroll-triggered auto-load variant of the pagination, built, watched in a real browser, and reverted in favor of plain pagination links once it didn't read as an improvement; a live, no-reload filter UI for alerts built in React, with TypeScript and esbuild adopted alongside it; tracking-event filters that apply automatically with no submit button; live search with no submit button on stores (address), products (name and brand, independently), and brands (name), via a generalized Stimulus controller, later reused to make every sort header on every page update without a reload, matching Alerts; and six rounds of external review response, including a test that catches the compiled JS drifting from its TypeScript source, a fix that cut `KeysetPage`'s per-request query count, and a CSV-export formula-injection guard. Two migrations add the index columns the keyset queries need. 94 tests total - 84 unit/integration/controller plus 10 real-browser system tests (Capybara + Selenium + actual Chrome, not a stub).

## The design held up, mostly

- **The filters are cheap, as predicted.** Status and brand both filter on existing indexed columns (`resolved_at`, `brand_id`) - no migration needed for either, matching `DESIGN_PROPOSAL_FINAL.md`'s claim exactly. Same for the tracking-event filters: the date range reuses the existing composite indexes' trailing `event_time` column, as predicted.
- **Keyset pagination's actual benefit held up under test**, not just in theory: `KeysetPageTest` round-trips a cursor forward and back to the exact same rows, confirms rows sharing an identical sort value still order consistently via the `id` tiebreak, and walks a boolean sort ("status") across 30 pages to confirm it crosses the open/resolved boundary cleanly rather than just working within one bucket. Two more committed tests, added after a later review round pointed out they'd only ever been checked ad hoc, cover the harder cases directly: sorting by a *joined* column (brand name) and by the computed status boolean, each crossing a real page boundary.
- **CSV export reads the same filtered, sorted scope as the HTML view**, per the proposal's "no new storage" framing - no separate export-specific query logic. The same is true of the alerts filter UI's `GET /alerts.json` endpoint, added later: one scope, three response formats.

## One place the first build didn't match the proposal - caught, then fixed

`DESIGN_PROPOSAL_FINAL.md`'s suggested scope called for "keyset infinite scroll." What got built first was keyset *pagination* - the query-level fix, exposed through ordinary link clicks, not scrolling. Caught by a direct question about where the scrolling actually was. Fixed by building real auto-loading (a Stimulus controller watching the "Next" link with an `IntersectionObserver`), verified with a real system test - scrolling the link into view with zero clicks loaded the remaining rows.

## One place the build matched the proposal, and the proposal was the problem

Auto-loading, once actually watchable in a real browser rather than read as a design doc, didn't read as an improvement - continuous loading with no visible page boundary read as "the page never ends," not as efficient. Reverted to plain, click-through pagination at 50 rows per page. The keyset mechanism underneath - the part that actually took engineering effort and carries the real correctness/performance property - is unchanged; only the auto-load trigger is gone.

## Sorting, extended to the tables it was originally scoped away from

`DESIGN_PROPOSAL_FINAL.md` originally kept sorting off alerts and the tracking-event lists specifically, reasoning that combining "sort by any column" with keyset pagination multiplies the complexity of both. That reasoning about the cost was right; the scope call built from it was revisited and reversed once asked for directly. What made it tractable: `KeysetPage` took the per-column cursor cost as a parameter (`direction:`, `id_column:`, `value:`) rather than a wall, then got reused across five sortable alert columns (brand, product, store, triggered-at, and a computed boolean for status), three tracking-event columns, and later a sixth alert-adjacent column (Brand, on the store show page's tracking-events table). Verified directly against real data via `bin/rails runner` before trusting any of it in the UI, not just read as correct from the code.

## Tracking-event filters: from a Filter button to automatic, and a scroll bug along the way

Built first as an ordinary GET form with a submit button. Changed to apply automatically on field change, which surfaced two real scroll-position bugs that weren't obvious from the code:

- Sorting or filtering the tracking-events table reset scroll to the top of the page, losing the user's place. Fixed by anchoring both the sort links and the filter form to a `#tracking-events` fragment on the card. Two separate bugs fought this fix specifically: Turbo Drive (loaded globally, unused everywhere else in this app) intercepts link clicks into its own "visit," which doesn't resolve a URL fragment the same way a real navigation does - fixed with `data-turbo="false"` on the sort links; and passing `anchor:` through `request.query_parameters.merge(...)` silently turned it into a literal `?anchor=` query parameter instead of a `#fragment`. Root-caused, not just worked around: `request.query_parameters` is an `ActiveSupport::HashWithIndifferentAccess`, which normalizes every key it stores - including a merged-in `:anchor` - to a String; Rails' URL generation only pulls out a literal Symbol `:anchor` key as the fragment, so a String `"anchor"` key inside a `HashWithIndifferentAccess` falls through as an ordinary query param instead. The identical merge against a plain `Hash` (or `request.query_parameters.to_h`) keeps `:anchor` a real Symbol and works correctly - it's that one class, not `helper_method` or mixed key types in general. Fixed by building the URL without `anchor:` and appending `#tracking-events` to the resulting string directly, which sidesteps the question entirely.
- The filter form's `action` attribute correctly carried the fragment, but Chrome drops a form's URL fragment on native GET submission - a real, documented cross-browser inconsistency. The auto-submit controller (`auto_submit_controller.ts`) builds the GET URL itself from the form's fields instead of calling `form.requestSubmit()`, so the fragment survives regardless.

## Live search, from one field on one page to a generalized controller on three

Built first as a single debounced text field on `/stores` (address), with an explicit "no submit button, populate as you type" constraint. Extended on request to `/products` (name and brand, as two independent fields that combine with AND) and `/brands` (name). The second extension required generalizing `live_search_controller.ts`, which had been hardcoded to a single `?q=` field: it now reads every field's current value, keyed by each field's own `name` attribute, on every debounced search - not just whichever field just changed - so more than one independent search field on a page works without any per-page JS. Every search column uses `sanitize_sql_like` against an `ILIKE` pattern, verified with a test that a literal `%` in the search term matches literally rather than as a wildcard (the specific correctness bug `sanitize_sql_like` exists to prevent).

## Sort headers reloaded the page everywhere except Alerts - a one-line root cause, not five separate fixes

Raised directly: clicking a column header reloaded the page on Products, Stores, and Brands, including the tracking-event tables on the individual product and store pages - but not on Alerts, which updates in place via React. The cause was one shared helper, not five separate problems: `sort_header` always set `data-turbo="false"` on every sort link it rendered, a fix that was only ever needed for the two show pages' tracking-event tables (Turbo Drive's own "visit" doesn't resolve a `#tracking-events` fragment the way a real navigation does). Every other sort click everywhere was paying for a fix it didn't need.

Fixed by extending `live_search_controller.ts` rather than adding a second mechanism: it already fetches a URL, swaps `[data-live-search-target="results"]`, and pushes the new URL for live search - a new `sort(event)` action does the same thing for a sort-link click, fetching the link's own `href` directly (already correct, built server-side) instead of merging field values the way `search()` does. `sort_header` gained `data-action="live-search#sort"` alongside the existing `data-turbo="false"`, which stays as the fallback for when JS or the controller isn't present. The three index pages were already wrapped in the `live-search` controller for search, so sort started working the same way there with no view changes; the two show pages' tracking-events card had no `live-search` controller on it at all (only `auto-submit`, scoped to the filter form) - added it, wrapping the table and pagination as the swap target, leaving the filter form itself untouched since changing it wasn't asked for.

One real gap caught before shipping: a sort link only gets one click, unlike a search field that can fall back to a real Enter-key submit if a fetch fails. Added a real fallback - `sort()` falls back to `window.location.href` if the fetch-and-swap fails - so a sort click never just silently does nothing.

Verified against the real dev server (inspecting the rendered `<a>` tag's actual attributes) and with new/strengthened system tests asserting `window.name` survives a sort click - a real navigation clears it, a DOM swap doesn't - on all five affected pages.

## Six bugs, caught by running the app or by a test that actually checked the right thing, not by reading the code

**The cursor's own encoding was broken from the start.** `KeysetCursor` originally joined a timestamp and a row id with `:` and split on the first `:` to decode - but an ISO8601 timestamp already contains colons, so decoding cut the timestamp itself in half. Every "Next" click silently re-rendered page one forever - wrong, not crashing, the more dangerous kind of bug. Caught by a round-trip test failing with the wrong rows. Fixed by switching to a typed JSON encoding (`[type, value, id]`), which also turned out necessary once sorting needed to encode strings and booleans, not just timestamps.

**`csv` isn't auto-required outside the test environment.** The CSV export passed its controller test on the first try, which made the gap easy to miss - something in the test boot path pulls in Ruby's `csv` stdlib transitively that the dev server doesn't. The real server 500'd with `NameError: uninitialized constant AlertsController::CSV` on the identical code. Caught by curling the export endpoint against a running server instead of trusting the green suite alone. Fixed with an explicit `require "csv"`.

**Two dropdown filters had their options exactly backwards.** The product/store tracking-event filters' "pick one store" and "pick one product" selects plucked `[id, name]` from the database, but `options_for_select` expects `[label, value]` - every option showed the row's *id* as the visible label and the *name* as what actually got submitted. Caught by a controller test that asserted on the dropdown's actual rendered options, not just that the page returned 200. Fixed by swapping the pluck order.

**A missing nested vendor file broke React silently.** The first working version of the React-based alerts filter failed in the browser with no visible error - `bin/importmap pin react react-dom/client` had vendored `scheduler.js`, but not `scheduler.js`'s *own* relative import (`./cjs/scheduler.production.js`), which it depends on. The browser's actual error - "Failed to fetch dynamically imported module" - doesn't say which module or why; tracing it required a throwaway diagnostic system test that imported each dependency individually in the browser until the real cause turned up. Fixed by fetching that one file to the matching relative path by hand.

**A test gave a false "bug" from a sloppy grep pattern**, not from the app. A date-range filter check matched a *different* table's dates on the same page. Fixed the check (via server logs showing the real SQL `WHERE` clause), not the app.

**A system test gave a false failure from reading the DOM too early.** Clicking a sort header in the React-based alerts UI appeared not to re-sort - because the test read the table immediately after the click, racing the async re-render. Fixed the test's wait condition, not the app.

## Six rounds of external review, each catching something real

**Round A.** Found the "keyset infinite scroll" gap above, a heading mislabeled over the wrong comparison's content (Postgres-search-vs-Elasticsearch's heading sat over the Plain-CSS-vs-Sass table), and a stale "four things" count after a fifth section was added. All fixed.

**Round B.** Caught three things that mattered: the tracking-event composite indexes were described as still-proposed when the schema already had them built; alerts sorted by brand/product/store genuinely have no supporting index, which hadn't been named; and the React-vs-Turbo-Frames comparison overstated what Turbo Frames can do - a GET form and links targeting one frame keep filters+sort+cursor in sync without a reload just fine, no hand-patched DOM required. The real reason for React is that this project is expected to grow more complex client-side logic over time, not that Turbo Frames couldn't do the job - the doc said the wrong thing for the right decision, and now says the right thing. Also requested and added: a request-flow/build-flow Mermaid diagram, the alerts filter UI's actual data path (`GET /alerts.json`), and the three questions a homemade TypeScript build step raises, answered plainly (output is committed; React is vendored, not CDN-loaded; Node isn't needed to run the app or tests).

**Round C.** Found a real gap in the build step itself: nothing caught the committed `app/javascript/controllers/*.js` drifting from the `.ts`/`.tsx` source that produces it, and there's no CI on this repo to catch it generically. Added `test/build_controllers_test.rb`, which re-runs the actual build and fails on any diff - skipping, not failing, on a machine without Node, so the "Node not required" claim stays true rather than becoming quietly false. Verified in both directions before trusting it: editing the compiled `.js` directly first passed the test, because its own rebuild step silently re-derived the correct output from the *unchanged* source before the diff check ran - not a bug, just the wrong way to simulate drift; editing the actual `.ts` source without rebuilding then failed with the expected message. Also caught: a stale index claim in the Sorting section, a still-proposal-tense "Recommendation" line for a feature that was actually built, review-process narration in the Search/Scope sections that belonged in `DESIGN_REVIEWED_PROPOSAL.md` instead, a forward-looking note that hadn't caught up to `/alerts.json` already existing, and an unused Rails scaffold file (`hello_controller.js`) nobody had deleted.

**Round D.** Found a real bug in round C's own build-drift test: it rebuilt directly into the committed `app/javascript/controllers/` directory and diffed against git, so running the suite could overwrite committed JS as a side effect, a rebuilt-but-not-yet-staged file would fail the test for no real reason, and `npx tsc` could try to download TypeScript on a machine without it. Fixed: `bin/build_controllers.js` takes an optional output-directory argument, the test now builds into a `Dir.mktmpdir` scratch directory and compares file contents directly to what's committed (no git index involved, nothing committed ever touched), and it calls `node_modules/.bin/tsc` directly instead of `npx tsc`. Also found a real inefficiency: `KeysetPage#next_cursor`/`#prev_cursor` ran a separate `EXISTS` query each, every request, cursor or not - fixed with the same limit+1 trick `Paginatable` already uses (fetch one extra row; whether it came back answers "more in this direction" for free), cutting it to zero extra queries on the first page and one once a cursor is set, verified with a real query-count measurement against Postgres and committed as two regression tests. Also found: the in-memory CSV export is a real scaling limit, now named explicitly rather than left unstated; a CSV formula-injection gap (a cell starting with `=`/`+`/`-`/`@` runs as a formula in whatever spreadsheet opens it), closed with a one-line `'` prefix and a test exporting a brand literally named `=1+1`; and a comment on the `anchor:` workaround that said "didn't repro in isolation," rather than naming a cause - tracked down for real this round (see the tracking-event-filters section above for the actual root cause: `request.query_parameters`'s class, not `helper_method` or mixed key types).

**After round D:** code comments in `alerts_filter_controller.tsx`, `alerts_controller.rb`, and `keyset_page_test.rb` cited "round 7"/"round 8" of `DESIGN_REVIEWED_PROPOSAL.md` by number - fine as a pointer while this file was being written, but the same review-process narration already flagged and trimmed from the proposal's prose (round 11). Removed; each comment now just states the technical reason on its own. The compiled `.js` was unaffected, since esbuild strips comments - confirmed via an empty `git diff` after rebuilding.

**Round E.** Three smaller, still-real findings. The round D comment explaining the `anchor:` root cause overcorrected into 12 lines for one line of code - trimmed to three. `csv_safe`'s `FORMULA_PREFIXES` covered `=`/`+`/`-`/`@` but not the two other characters on OWASP's CSV-injection list, a leading tab or carriage return - added both. And the build-drift test itself crashed with `Errno::ENOENT` instead of failing cleanly when a new `.ts`/`.tsx` file had no committed `.js` counterpart yet - a real scenario, not hypothetical. Reproduced directly (added a throwaway source file, watched the crash), fixed with an `exist?` check, reproduced again to confirm it now fails with the intended message instead, then removed the throwaway file.

**Round F.** `DESIGN_PROPOSAL_FINAL.md`'s own opening still read as if nothing had been built: "proposed before any app files change" and "the rendered comparison is in the artifact" - meaningless to a reader without that artifact open, and stale once Option A was actually chosen and built. Rewritten to state what happened, past tense. "No new dependencies in any of the three" was true for CSS specifically but read as a contradiction once React/TypeScript were added later - narrowed to "No new CSS dependencies." "Nothing in `app/` changes until one is picked" was flatly false by the time anyone was reading it - the section was retitled and reworded as a historical record of the mockup comparison, not a live caveat. Three more bare "the artifact" references, meaningless outside this conversation, reworded or dropped.

## Verified by running it, not just by the test suite being green

- Followed a real "Next" link's cursor through `curl` and confirmed the alert IDs on the second page were genuinely different from the first, not a repeat.
- Downloaded the actual CSV export via `curl`, confirmed the `content-type`/`content-disposition` headers and that the row count matched the active filter.
- Watched a real Chrome window auto-load alerts on scroll (before that was reverted), and separately watched the React-based filter UI change results and the URL with no page reload, confirmed via `window.name` surviving the operation - a real navigation clears it, a DOM update doesn't. The same `window.name` check later confirmed the generalized live-search controller doesn't reload either, on three different pages.
- Measured real scroll position (`window.scrollY`) before and after a sort/filter click in an actual browser to confirm the anchor fix actually lands back on the table, not just that the link's `href` looks right.
- Deliberately introduced real drift into the TypeScript build twice - once the wrong way, once the right way - to confirm the new build-drift test actually distinguishes them, before trusting it.
- Added a throwaway, uncommitted `.ts` source file to confirm the build-drift test's missing-committed-file case actually crashed before the fix, and actually failed cleanly after it - not just inferred from reading the new `exist?` check.
- Subscribed to `sql.active_record` notifications around real `KeysetPage` calls to count actual queries before and after the limit+1 fix, rather than reasoning about it from the code - 0 extra on a cursor-less page, 1 once a cursor is set, matching the fix's own claim exactly.
- Reproduced the `anchor:`-swallowing bug live against the running dev server with a temporary debug route (removed once the cause was confirmed), rather than guessing from the code which class `request.query_parameters` actually is.
- Inspected the real dev server's rendered `<a>` tags for every sort header to confirm `data-action="live-search#sort"` was actually present, not just that the helper code looked right, and used `window.name` the same way as the live-search checks above to confirm a sort click never navigates - on all five affected pages, not just one.

## What's still a known limitation, not silently dropped

The infinite-scroll usability notes in `DESIGN_PROPOSAL_FINAL.md` are moot rather than solved or unsolved - there's no auto-loading left for any of them to apply to. The one real limitation that survives the revert: the browser Back button on the React-rendered alerts page works correctly (it's `history.pushState`-backed, same as a real navigation), but nothing preserves scroll position within the list itself if someone navigates away and back - not a problem with plain pagination, worth stating here in case the UI changes again later.

This app's homemade TypeScript build (`tsc` + `esbuild`, output committed, no `jsbundling-rails`) is a deliberate choice to keep what's already built and tested rather than the better long-term choice if the frontend grows further - stated plainly in `DESIGN_PROPOSAL_FINAL.md` rather than presented as the obviously-correct architecture.
